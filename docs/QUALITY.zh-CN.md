# 质量优先请求策略

本实验评估现有 `ghcr.io/loon-hejw/sglang-deepseek-v41-flash-sm120-compat:v0.4.4-rc.4` 镜像与锁定的 1017 权重所支持的请求策略，不训练权重、不修改服务镜像。此前测量与工具字面量限制见[测试总览](../TESTING.zh-CN.md)。

## 2026-11-05 实测结果

**整套策略未通过全部验收，保持实验状态。** 留出集从 388/700（55.43%）提高到 511/700（73.00%），提升 17.57 个百分点；按题族 bootstrap 的 95% 区间为提升 5.00 至 30.57 个百分点。质量、速度、旧题回归和代码对照通过，但非流式工具字面量对照从 2/60 降到 1/60。工具两侧参数相同，因此不能把差异归因于参数调整；仍须按预先确定的“不退步”规则判定未通过。没有用重试替换失败，也没有放宽门槛。

共完成 2,979 次计分观察和 140 组测速。公开证据包括[汇总与来源](../compat/quality-policy-20261105.json)、[逐请求记录](../compat/quality-policy-20261105-results.json)、[逐批测速](../compat/quality-policy-20261105-speed.json)及[实验预设](../examples/quality-policy-profiles.json)。计分请求没有协议错误，但模型答错和截断仍计入失败。生产服务容器、启动时间保持原样且健康；测试实例已停止，0731 保持停止。

两组请求使用相同四张 RTX PRO 6000 Blackwell、相同服务实例，TP4 / Attention DP1 / EP2，DSPARK block 5 / SPS auto，FP8 KV、1M 上下文上限、224 GiB 主机内存、16 CPU。权重修订为 `1bae0e1088993b9b82de08f59de5be5a34e42170`，运行镜像摘要为 `sha256:0a32f40290db16a139ee2ac38ec4a8641b7310de07b79a249dd1c11d46a48a92`。实际最长输入为 262,132 tokens。

### 评测器修正与适用范围

初次 API 探针把一道算术答错误当作启动失败；筛选开始前已改为检查协议完整性与实际思考模式，答错仍计分。之后在完成 217 次留出观察后，于已保存检查点暂停，改为每次 CPU 代码判分分配独立容器名，避免并发相同代码共享容器名；修正前没有观察到此类冲突失败。修正后四个并发相同参考程序全部通过。前 1,392 条观察（含 217 条留出记录）在独立版本目录中原样继承，公开记录包含源码哈希、原提交和结果摘要。没有重试已完成请求，没有修改模型请求、候选预设和判分规则。

测试实例三次启动分别观察到 292.93、282.84、282.94 秒，初始编译缓存从已有服务复制。这是运行观察，不是受控热启动基准，也不承诺其他主机耗时。合成题、十四个留出题族、重复前缀缓存及单一硬件配置限制了结果的推广范围；收益支持继续按任务验证，不支持宣称普遍质量提升或直接修改全局默认值。

## 调整内容

思考强度是给模型的指令，不是严格的思考 token 配额，也不会为最终答案预留固定预算。当前编码器将 low 映射为 50、medium 为 62、high 和 xhigh 为 75、max 为 100。启用思考但未指定强度时，默认强度为 high；是否启用思考是另一个开关。当前未设置 SGLANG_DEFAULT_THINKING 的实例中，同时省略 reasoning_effort 与思考开关会进入非思考模式；显式传入非 none 的 reasoning_effort 会启用思考，除非调用方通过 chat_template_kwargs 显式关闭。实际 tokenizer 核对确认：省略控制字段与显式关闭思考的编码相同，显式 high 与 thinking=true/high 的编码相同。更高强度可能帮助复杂任务，也可能增加等待或耗尽输出预算；当前构建的 xhigh 不比 high 更强。

主对照显式使用 temperature 1、top_p 1；推理任务 high，代码采用此前选出的 low，其他类别关闭思考。推理和代码预算 12,288，工具 4,096，其他 2,048。这是明确的评测请求，不代表所有线上客户端实际发送的参数。

筛选阶段对推理、代码比较 low/medium/high/max，再对得分最高的两组增加 24,576-token 预算，最后对最佳组合测试 temperature 0.6。其他类别比较 none/low/medium，再对最佳组合测试 temperature 0.3 和 0.6。top_p 始终为 1；惩罚参数专项的请求字段在各策略间保持一致。记录最终生效参数与请求哈希。

[请求客户端](../examples/quality-request.py) 可将指定任务预设应用到含 model、messages 的普通 JSON 请求。调用方显式字段优先，包括 temperature=0、chat_template_kwargs.thinking=false；显式 max_completion_tokens 会替代预设中的 max_tokens。`--dry-run` 只打印最终请求，不发送。未通过验收的配置需要显式 `--experimental` 才可试用。客户端返回原始 completion JSON，拒绝截断或只有思考而无最终结果的响应，不执行工具、不自动重试。应用仍需校验工具语义和生成代码。

JSON Schema 只描述输出契约，不通过 const 或 enum 填入参考答案；数组内的可空字段始终允许 null。工具调用检查函数、次数、类型和解码后的完整参数，不实际执行工具。格式有效不等于内容正确。工具 schema 和 JSON 响应约束不在同一请求中叠加。

可先检查实验请求，不实际发送：

```bash
cat > /tmp/quality-request.json <<'JSON'
{"model":"deepseek-v4.1-flash-1017","messages":[{"role":"user","content":"只返回这些数字按升序排列后的 JSON 数组：12、3、8。"}]}
JSON
python3 -B examples/quality-request.py \
  --request /tmp/quality-request.json --category instructions \
  --experimental --dry-run
```

移除 `--dry-run` 并传入 `--base-url` 才会向指定端点发送。`penalties` 预设只选择思考强度、温度和预算，不把评测使用的非默认惩罚参数套到普通请求。客户端不自动猜测任务类别，也不注入新的系统提示词。

## 复现实验

运行器需要独立、已启动的推理端点，以及用于隔离执行代码的 Docker。运行器不管理服务、不改变服务配置；共享主机应另加资源监控。模型镜像已包含 Python，可用其本地固定摘要作为 CPU 判分容器。

```bash
python3 -B scripts/test_quality_eval.py
python3 -B -m scripts.quality_eval.run \
  --base-url http://127.0.0.1:8000/v1 \
  --model deepseek-v4.1-flash-1017 \
  --sandbox-image ghcr.io/loon-hejw/sglang-deepseek-v41-flash-sm120-compat:v0.4.4-rc.4@sha256:0a32f40290db16a139ee2ac38ec4a8641b7310de07b79a249dd1c11d46a48a92 \
  --output artifacts/quality-policy-local
```

需要鉴权时通过环境变量 `INFERENCE_API_KEY` 传入，结果不记录凭据。输出目录含原始答案和生成代码，须保持私有。只有按字段白名单导出的 public-summary.json、public-results.json 和 public-speed.json 用于发布前审查与脱敏。

运行器在筛选前冻结源码哈希、题目和方法，逐条保存结果；源码或方法变化时拒绝原地续跑。续跑不覆盖失败记录。在输出目录创建 `STOP_AFTER_BATCH` 可在活动请求保存后停到检查点，续跑前须移除该文件。单独版本的续跑目录可以记录原源码哈希、原结果摘要及继承的观察标识，用于有记录的评测器修正，不用于根据留出答案重新调参或替换失败。一个阶段内出现三次 API 错误会停止供检查。单请求有 900 秒安全截止时间，与“完整答案耗时不设质量验收门槛”分开处理。

## 证据与验收

新增 210 个任务实例来自 21 个题族：筛选集七个题族、每族十例；留出集十四个题族、每族十例。两集合题族不重叠。同族实例具有相关性，不能视为 210 项独立能力。筛选每组重复三次，留出集五次。原有 51 道有效合成题另做温度 0/1 回归，并保留 low 代码对照和非流式工具检查。留出结果不参与再次调参。

短质量请求在同一实例上最多并发四个，长输入串行。新增长输入由 tokenizer 校准至 32,768、131,072、262,144 tokens 的 1% 范围内，同时记录实际 usage；不据此验收完整 1M 上下文。请求 seed 成对记录，但未启用后端确定性推理。

预先确定的质量门槛为：七类等权平均通过率至少提高三个百分点，按类别分层、按题族重采样的 95% bootstrap 区间下界大于零，且任何类别下降不超过两个百分点。留出集只有十四个题族统计单位，不能扩展为广泛业务可信度。旧题分项、low 代码对照及非流式工具对照还须无退步；框架 CPU 解析回归另行记录。

测速每类使用一道固定筛选题，双方统一限制 1,024 输出 tokens，每组先预热四次，再在 C1/C4 各做五轮配对测量，交替测量顺序。速率为包含思考的 completion tokens 除以整批墙钟时间，包含首 token 等待；重复前缀保留缓存。每类、每个并发档的吞吐中位数须达到基线 80%。分别记录首 token、首个答案内容、完整回答时间；思考 token 增加不等于有效答案增加。短回答与思考变化可能使速率波动，因此保留逐批数据。

源码检查通过或筛选阶段胜出，均不足以推荐新配置。必须通过冻结后的留出集与性能门槛；未通过的实验参数不替换既有默认值。
